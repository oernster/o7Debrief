# Architecture

o7 Debrief is a local-first desktop application that turns the Elite Dangerous player Journal into a Commander Mission Debrief. It is a desktop executable, not a web app and not a local server. A Linux Flatpak is published with each release and has produced a debrief from a real journal on Ubuntu, with the game running under Proton and the report opening in a browser on the host; where the structure differs on Linux it is noted below (see [TECH_DEBT.md](TECH_DEBT.md) item 2 for the narrower assumptions that remain unproven). This document states the structural invariants first, then the components, the dependency direction, the execution flow and the rationale behind the decisions that shaped the design.

The governing idea: a debrief is a deterministic function of the journal bytes for one session. Everything else (a tray, a one-shot command, an export format) is plumbing around that function. The architecture exists to keep that function pure, the data real and the layers honest.

The organising distinction inside that function is between a **level** and an **event**. A level is a state the journal states outright: a credit balance, the active ship, a rank percentage, the current star system. It persists until something changes it, so the last known reading stays valid and may be carried forward from earlier history. A level therefore has an age as well as a value, which the credit balance is the case that proves: the journal states it at a login and never again, so the report carries the moment of the reading beside the figure rather than presenting a level hours old as a current one. An event belongs to the session that produced it: a jump, a bounty, a scan. Levels are read from the raw events and passed into the domain as readings; events are folded from moments. Confusing the two is what makes a report say zero where it should say nothing was read, so the split is structural rather than stylistic: `assemble()` derives no level at all.

The session's net credit change is where that distinction earns its keep, because it looks like an event fold and is not one. Folding the moments totals only what the journal itemises, which is income: a rebuy, an outfitting bill and a hold full of tritium leave no credit delta on any moment, so a session that lost twenty million credits reported a gain of two hundred thousand. The change is therefore derived from the level instead, as the difference between the first and last balance the journal stated in the session. What the moments can honestly say is a different figure with a different name: the total of the events the journal does price, reported beside the balance rather than inside it. That figure needs no rule to price an outgoing and cannot be wrong about one it has never heard of. It is optional for the same reason every level is: a session stating fewer than two balances has no measurable change and reports none rather than a zero.

## Layers and components

The package is `o7debrief`, split into four layers plus a single composition root. The dependency arrows always point towards the domain.

```
        +----------------------------+
        |            ui              |   PySide6 tray + minimal windows
        +-------------+--------------+
                      | imports application only (I2)
                      v
        +----------------------------+
        |        application         |   use cases, ports, orchestration
        +-------------+--------------+
                      | imports domain + stdlib only
                      v
        +----------------------------+         +----------------------------+
        |          domain            | <------ |       infrastructure       |
        |  pure stdlib, event-time   | impl.   |  journal IO, config, files |
        +----------------------------+ ports   +----------------------------+
```

### domain

Pure Python on the standard library. Frozen dataclasses with `slots`, `tuple` collections and validation on construction. The domain holds:

- The journal-event value objects and the session-moment model that raw events roll up into.
- The deterministic reducer that folds a sequence of parsed events into the moments for one session, working entirely in event-time read from journal timestamps.
- The `SessionDebrief` aggregate: the finished, render-ready view of a session, including rank changes (tier-ups now, percentages deferred), built only from real journal fields.

The domain reads no clock, opens no file and logs nothing. Time comes in as data on the events. This is what makes a debrief reproducible.

### application

The domain plus stdlib only; it never imports infrastructure or UI. It defines the ports (Protocols) that infrastructure implements and the use cases that orchestrate a debrief:

- A journal source port that reads only what a debrief needs: path discovery, an incremental byte-offset tail for the live watcher, a bounded read of the latest session (back only to the previous `Shutdown`) and a per-file streaming read for the all-history debrief, so no path loads the whole journal into memory. A clock port covers the few places that legitimately need wall-clock time (the crash-timeout safety net), kept out of the domain.
- An exporter port, a configuration port and a release-source port that supplies the latest published release (version, releases page and installer assets) for the update check. Beside the single-document exporter and sink sit a bundle exporter and a bundle sink, for a report too large to be one file: the exporter returns relative paths and bytes, so the application never learns what a directory is; the sink reports what it wrote and what it skipped.
- A text-template renderer port that words each timeline row from the template its taxonomy rule declares, rendered against the raw journal payload the moment carries. Rendering needs a template engine, which is third party and so belongs in infrastructure; this keeps the application on the domain and the standard library. The port returns nothing rather than a partial render when the payload cannot satisfy the template, so a row states its kind instead of a sentence with a hole in it; a reader is never shown a gap they would take for a fact.
- The paging of a whole-history log, which is a decision about the report rather than about its markup and so is settled here rather than in a renderer. The log is split into pages keyed on the calendar month they cover, each month filled from its oldest row forward; the day headings are recomputed for every page and every tab from the rows that page holds. Two further services bound rather than divide the report: a daily rollup that folds the older tail into one row per day per category, measured back from the newest row rather than from a clock so the same journal always renders the same way; and a cap for the one-document mode that trims the log and words the shortfall into the footer.
- The use cases: a live watch loop that debriefs the session at shutdown, a one-shot debrief of the last session and a one-shot debrief of the full history to date. The all-history use case folds the journal file by file, keeping only the moments, the state-bearing events and the window endpoints rather than every event at once. Every path calls the same domain reducer.
- An update service that compares the running version against the latest release through a pure version comparison, honours a caller-supplied skipped version (so a release the player skipped never prompts again on the automatic checks) and selects the platform's own installer asset by filename suffix, so the ui can offer a direct download with the releases page as the fallback. It is the only application service that touches the network and it reaches it solely through the injected release-source port.
- The level folds, one per state the journal reports outright: the active ship over time (so a death names the hull flown at that instant rather than the one the session ended in), the systems visited, the credit balances and the readings gathered around each death. Each takes raw events and returns a small immutable history the builder passes into the domain as a reading. The balance fold yields three: the latest reading as the level, the moment that reading was taken and the difference between the first and last as the session's net change. They live here rather than in the domain because they read the journal's own vocabulary, which is configuration to the domain, not part of it.
- A field diagnostic that reports when a taxonomy rule names a payload field the matching event never carried (or carried in a form the reader could not use), so a value the report could not read is stated instead of printed as zero. It watches the magnitude field as well as the currency field, because the jump-distance defect proved that a field can be present, named correctly and still go unread.

A use case may itself be an immutable object holding its injected dependencies.

### infrastructure

Implements the application's ports against the real world; it is never imported by the domain or the application. It owns:

- Journal IO: Journal directory discovery, the incremental byte-offset tail that reads only new bytes, a newest-first backward read that stops as soon as it has bracketed the latest session, a per-file batch iterator for streaming the whole history and the parse skeleton. The tail and discovery are reused from the author's EDColonisationAsst, which already solves Journal path discovery and incremental tailing.
- Configuration loading from TOML via stdlib `tomllib`, supplying the event taxonomy and any tunable values so the domain stays free of magic numbers.
- Exporters: the Jinja2 HTML renderer (inlined CSS, zero JavaScript), the HTML bundle renderer for a paged history and the Markdown renderer, plus file writing. The two HTML renderers share one stylesheet source, so a session report and a history report cannot drift apart in palette or layout; the single-file report inlines it and the bundle writes it once as `style.css` for every page to link. The bundle sink compares the bytes it is about to write against the bytes already there and leaves an unchanged file alone, which is what makes regenerating on every quit cheap; it also removes generated pages the bundle no longer contains, scoped to its own pages directory and its own file type. Each timeline row renders its activity (domain) glyph with the control mode shown as a compact tag, so a row reads as what the Commander did rather than which control mode held it; a death row additionally names who destroyed the Commander or else the cause (a self-destruct), a ship-launched-vehicle row (the Nomad vessel or a fighter) names the vehicle type, a bounty row names the destroyed ship and a completed-mission row names the mission (an Operation carries a readable title) with its faction and any Merc Coins it paid, all read from the moment detail by a dedicated `timeline_text` builder in the application layer. Every other row is worded from the template its taxonomy rule declares, rendered against the raw journal payload by a strict Jinja2 adapter behind the text-template renderer port: a row names the blueprint, grade, module and engineer of an engineering roll (or both sides of a material-trader exchange) rather than repeating the name of its kind. Undefined names are strict, so a template the payload cannot satisfy yields nothing and the row falls back to its label. The session log is ordered most recent first.
- The autostart adapters, one per platform behind a single shape, so the Settings dialog and the composition root are written against the shape rather than either implementation. On Windows the "start when I sign in" setting is an HKCU Run value; on Linux it is an XDG autostart desktop entry. The command each writes differs by how the app was delivered: a packaged build launches itself, a source checkout launches through the interpreter and a flatpak must be launched as `flatpak run` of its application id, because the entry is written for the host session to run and neither the interpreter nor the source tree exists out there. The same reasoning decides where the entry goes. A flatpak redirects `XDG_CONFIG_HOME` to the app's own private configuration, so honouring that variable inside the sandbox writes the entry somewhere only the app can see; under a flatpak the adapter therefore ignores it and writes to the session's real `~/.config/autostart`, which the manifest grants. The failure this prevents was silent in both directions, since the same adapter read its own private copy back and reported the setting as enabled.
- A GitHub release source for the update check: a single short, best-effort HTTPS GET built on the standard-library `urllib` (no third-party HTTP dependency), returning the latest published release (version with the tag's leading v stripped, releases page URL and well-formed assets) or None on any failure. The endpoint returns only published, non-draft, non-prerelease releases, so a tag pushed mid-development can never prompt.

### ui

PySide6, the client of the application layer only. It owns the system-tray icon and menu, the minimal windows and the user actions (debrief the last session, debrief the full history to date, choose export format and open the home screen). It holds no domain logic; it calls use cases and displays their results.

It also owns the two halves of what one running copy means. A per-user single-instance lock, an OS-level exclusive lock on a file the operating system releases when the process dies, so a crash never strands a stale lock. Beside it sits the summon marker: a second launch that finds the lock held leaves a marker file in the same directory and exits; the running copy polls for that marker and opens its home window. The app has no window of its own, so launching it again is the standing route back to it and reaches the same surface the tray icon does, whatever the desktop does or does not draw. Inside a flatpak both files move to the runtime subdirectory the sandbox shares between instances of one application, since each instance is otherwise given a private one and would neither take the same lock nor see the same marker.

Whether there is a tray to live in at all is treated as a property of the running desktop, never of the operating system. Windows always draws one; a Linux desktop need not, since the same distribution answers differently depending on which shell extension or panel is installed and whether the user has it turned on. So the app asks Qt what this desktop provides rather than reading the platform name; it asks repeatedly over a short grace period rather than once: launched from the autostart entry, it is up before the panel that would host the icon has registered; a single check there reports no tray on a machine that is about to have one. The answer settles once. With a tray, the icon is shown again, since it was first asked for when there may have been no host to attach it to. Without one, the home window opens, so the app is never left running with nothing on screen to click. That asymmetry is deliberate: a redundant window costs a click, an unreachable background process costs the app.

### Composition root

A single `main.py` constructs the concrete infrastructure adapters and injects them into the application use cases, then hands those to the UI. This is the only place wiring happens (I5). There are no module-level singletons.

The running version is injected from here too, because it is a fact about the build rather than a display string. The presenter requires it, so a report cannot be produced by a caller that does not know what version produced it.

### The setup program

The `installer` package is a second, self-contained program that ships the first one. It imports nothing from `o7debrief` and is deliberately dependency-light: process detection is `tasklist`, version comparison is a tuple compare and shortcuts are written through the Windows scripting host, so the compiled onefile pulls in nothing beyond PySide6 and the standard library.

It follows the same shape as the application, for the same reason. `ops` holds the side effects (payload extraction, paths, shortcuts, process control and the install, repair and uninstall sequences) and `state` holds the HKCU registrations, version comparison and the state model the window reads. Neither imports Qt. `ui` is the only Qt client, `shared` holds resource resolution and crash logging, `cli.py` parses the command line the registered `UninstallString` re-invokes and `app.py` is the composition root.

The split is what makes two behaviours possible without a Qt dependency leaking into the work. A sequence in `ops` reports its phase and its progress through an injected callback, so `ui` can run the whole sequence on a worker thread and drive a progress bar from it while the window stays responsive; the sequence itself knows nothing about Qt. Payload extraction resolves each archive member against the resolved install directory and refuses any entry that would land outside it: the bundle comes from this project's own build tooling, so an escaping entry was never the expected case; extraction nevertheless runs with the user's full privileges, which is reason enough to enforce the property rather than assume it.

Three seams keep the privileged work testable, which is what allows `installer.ops` and `installer.state` to sit inside the 100% gate:

- every external command goes through an injectable `CommandRunner`, so no test spawns a process it did not intend to;
- the HKCU locations are a `RegistryKeys` value rather than constants baked into each function, so a test writes to a scratch key instead of the user's own registration;
- the per-user directories come from environment variables, so the suite redirects the profile into a temporary tree.

`shared` also holds the setup program's diagnostics, which cover more than crashes. The worst failures here are the quiet ones: an install that reports success and starts nothing; a window that closes with the work half done. Neither raises, so neither leaves a traceback; by the time a user reports it the machine has usually been changed again and the evidence has gone. So each step is appended to a log as it happens (which action was chosen, the installed and bundled versions, whether the running application was closed, whether the launch afterwards worked) alongside the unhandled-exception hook. Logging is best effort throughout: a log that cannot be written never becomes the reason an install fails.

Ending the running application is a forced terminate of the named image and nothing else. It once carried the tree flag as well, which ends the target plus everything Windows considers descended from it; the setup program twice died at exactly that call while the application closed perfectly. The application starts no children that need ending, so the flag bought nothing and cost the setup program its own life. A test pins its absence, because nothing had ever pinned the argument list and that is how it survived unnoticed.

The launch that follows an install is reported rather than assumed. It used to swallow any failure to start the application and return nothing, so the setup program could not tell a launch that happened from one that did not; it reported success and closed itself, leaving the user with no application, no window and no explanation. The runner now returns whether the process started and the window stays open and says so when it did not. The install itself succeeded in that case, so the wording separates the two.

The entry point is `installer_main.py` at the repository root rather than a script inside the package. A script is compiled with its own directory on the module search path, so compiling `installer/app.py` directly would leave the `installer.*` imports unresolvable. Compiling from the root also gives the payload one anchor that holds in both source and compiled runs: it is resolved relative to the `installer` package directory; `buildinstaller.py` includes the staged payload at that same relative location.

## Execution flow

The same core path serves both capture modes. The difference is only where the journal bytes come from and what triggers the render.

```
journal bytes  ->  parse (infrastructure)  ->  reducer (domain)
                                                   |
                                                   v
                                            SessionDebrief (domain)
                                                   |
                     +------------+------------+-------------+
                     v                         v             v
             HTML exporter            HTML bundle       Markdown exporter
          (one self-contained         exporter          (Discord / Reddit
           file: inlined CSS,      (whole-history        paste format)
           zero JavaScript)         runs only: an
                                    index, a page
                                    per month and
                                    one style.css)
```

A session always takes the single-file path. A whole-history run takes the
bundle path where a bundle exporter exists for the requested format, which is
HTML alone; Markdown and the opt-in one-document mode fall back to the
single-file path with the log capped and the shortfall stated in the footer.

Live watch path: the watcher polls the active Journal at a low frequency, tails new bytes from the last offset and feeds parsed events to the reducer, retaining only the session in progress so a watcher left running for days stays bounded in memory. On a `Shutdown` event it generates the debrief automatically; a crash-timeout acts as a safety net so a session that ends without a clean `Shutdown` still produces a report.

Cold one-shot path: "Debrief my last session" reads the newest Journal files backwards, stopping as soon as it has seen enough `Shutdown` events to bracket the latest run (typically the newest file or two), runs the same reducer and renders the same `SessionDebrief`. It never reads the whole history and works even if o7 Debrief was not running during play. "Debrief my history to date" does cover every event but streams the journal one file at a time, folding each file into a bounded summary rather than loading it all at once. It renders differently as well: the log is split into pages and written into one stable bundle directory, rewritten in place on each run, so what the reader opens is always the current history rather than another dated snapshot beside the last one.

Session isolation is by `Shutdown` bracketing: the latest session is the run ending at the last `Shutdown` (or the end of the log when the game closed without one), starting just after the previous `Shutdown`. Every `LoadGame` within that run, including those a return to the main menu fires, stays in the session, so an earlier session never enters the reduction.

Rank handling reflects what the journal can actually tell us. A `Promotion` (a tier-up) is reported in the session it happens. Fractional rank percentages are only snapshotted by the journal at startup, so they are finalised at the next launch; only ranks that changed are shown, never a full unchanged ladder.

## Design-decision rationale

### Core feature and output decisions

| # | Decision | Why | What it rules out |
| --- | --- | --- | --- |
| 1 | Ship both capture paths in v1 (live background watcher and cold one-shot). | The two paths cover the two real situations: app running during play and app not running but you still want a debrief. One shared reducer keeps them consistent. | A v1 that only worked if you remembered to start the app first or only worked as a manual after-the-fact tool. |
| 2 | HTML and Markdown in v1, with a configurable default format overridable per export. | HTML is the canonical, self-contained, portable artefact; Markdown is what you paste into Discord or Reddit. A default keeps the common case one click; per-export override keeps it flexible. | Locking users into a single format or forcing a format choice on every single export. |
| 3 | Real data only: every number traces to a journal field. | Trust is the product. A debrief that estimates or guesses is worse than no debrief because the reader cannot tell which figures are real. | Derived or interpolated statistics that look authoritative but cannot be verified against the journal. |
| 4 | Pure-Python Windows executable now; a Linux port later if there is demand. | The audience is on Windows; a Nuitka standalone exe ships without asking users to install Python. Pure Python keeps the Linux port a packaging exercise, not a rewrite. The port has since been written and the prediction held: it cost a packaging script and one autostart adapter behind the existing shape, with no change to the domain, the application layer or the reducer. | A cross-platform v1 that delays the Windows release the audience actually wants or a native rewrite per platform. |
| 5 | Strict UI boundary: the UI imports the application layer only. | It keeps the UI swappable (tray today, more later) and keeps domain logic out of widgets, which is where logic goes to become untestable. | A UI that reaches into the domain or infrastructure and quietly becomes the place business rules live. |
| 6 | Ranks as tier-ups-now plus percentages-next-launch, showing only changed ranks. | It matches what the journal records: promotions are events but progress percentages are only snapshotted at startup. Reporting them this way is honest rather than fabricated. | Inventing a mid-session percentage the journal never recorded or padding the report with unchanged ranks. |

### Keystone decisions

| Decision | Why | What it rules out |
| --- | --- | --- |
| A desktop executable, not a local server. | The tool reads a local file and writes a local report; a server adds ports, lifecycle and attack surface for no user benefit. Local-first keeps the player's data on the player's machine. | A background HTTP service, a browser-based UI talking to localhost, any inbound network surface. The one exception is the update check: a single anonymous outbound GET, run shortly after launch, once a day and on demand from the tray, which never downloads or runs anything without the player choosing Download and fails silently on the automatic paths. |
| A second launch summons the running copy through a file, never a socket. | The app has no window of its own, so where no system tray is drawn it is unreachable; launching it again is what a user tries; it did nothing visible. The obvious mechanism, a local socket the running copy listens on, is the one thing the keystone above rules out: it would give the app an inbound surface to defend and a port to own, to save a window nobody can open. A marker file in the directory that already holds the single-instance lock costs a poll of one stat and stays entirely on the filesystem. The marker carries no instruction either, only its own presence, so a second process can ask to be seen and can direct nothing. | A listening socket, a local port, an inbound surface of any kind; a second process able to tell the running one what to do. |
| Batch reporting, not live. | The value is reflective: a coherent end-of-session summary. A live feed is a different product (an overlay) with different constraints. | Real-time on-screen updates, an in-game overlay, continuous streaming of partial state. |
| TOML configuration for the event taxonomy. | The mapping from raw events to moments is data, not code; holding it in TOML (read with stdlib `tomllib`) keeps magic numbers and domain-specific mappings out of the logic and makes the taxonomy reviewable. | Hardcoded event-to-moment mappings and tuning constants scattered through the codebase. |
| A data-driven where-filter on a moment rule. | Some journal events are shared across many subjects and only become a specific moment when one payload field carries a distinguishing token. The Nomad reuses `LaunchFighter` to deploy (a Nomad deployment only when its `Loadout` is one of the vessel variants) and `ModuleBuy` covers the Vessel Hangar (a hangar purchase only when the item name contains `fighterbay`). A rule may name a `where_field` and a list of `where_contains` tokens, matching when the field contains any of them, so the discriminator lives in the taxonomy rather than as an event-name-specific branch in code. Some events are told apart by which field is there rather than by what a field says, so a rule may instead name a `where_present`: an `EngineerCraft` that applies an experimental effect carries `ApplyExperimentalEffect` and a grade roll does not, while both carry the blueprint and the grade. One event can carry several candidate rules (the Nomad and every fighter share `LaunchFighter`); the reducer uses the first whose filter matches, so taxonomy order sets precedence. The phase tracker reads the same Nomad-deployment discriminator from the taxonomy rather than hardcoding loadout strings. Adding a variant or correcting a game-side rename is a one-line config edit. | Per-event conditional logic in the reducer; hardcoded module, loadout or item identifiers in the domain. |
| Row wording lives in the taxonomy as data and renders strictly. | What a timeline row says is presentation; presentation over journal fields is configuration for the same reason the event mapping is, because it changes with the game rather than with the logic. Each rule therefore carries a template rendered against the raw payload, so naming the blueprint, grade, module and engineer of an engineering roll is a config edit rather than a code change. Rendering is strict about undefined names: a template the payload cannot satisfy produces nothing and the row falls back to naming its kind, because a half-rendered sentence is worse than a plain one. The engine sits in infrastructure behind a port so the application layer stays on the domain and the standard library. | Row wording hardcoded per event type in the presenter, which is what four conditional kinds already cost and what thirty would have cost; a lenient render that prints "Applied Weapon_Overcharged grade 5 to  at ." and lets a reader take the gaps for facts. |
| Journal tokens are decoded into English structurally, with the vocabulary in the taxonomy. | The journal states no readable name for a module: across 182 fitted modules in a real journal, not one carried an `Item_Localised`, so there is nothing to look up and the English must come from the token. The decode is therefore structural rather than a product dictionary; every word it emits is a transliterated part of the token, a substitution the taxonomy names or a rating letter from the taxonomy's own table. A part with no entry is title-cased and kept, so a vocabulary gap shows up in the report as an odd word rather than as a module that silently loses half its name. | Printing `int_sensors_size5_class2` at a Commander; a hardcoded product dictionary in code, which would need a release to correct a game-side rename; dropping an unrecognised part, which would report a different module from the one that was engineered. |
| A material trade is a trade moment with no credit figure. | A material-trader exchange is paid for in materials and the journal states no price for it, so there is nothing to read into either credit column. The Trade rollup counts the exchanges beside the market figures instead, which is what lets a session that traded 31 times at the traders and bought nothing on any market report both truthfully at once. | Pricing the exchange with an invented figure; folding it into spend or earnings; leaving material trading out of the report entirely, which is what happened while the event had no rule at all. |
| Merc Coins as a separate currency channel from credits. | Operations pay a Merc Coins reward alongside credits; coins are not credits. A moment carries a distinct `coins_delta` beside its `credits_delta`, summed into the Missions rollup's own `coin_rewards` total, so coins never join a credit figure. The coin field is read from a taxonomy-named `coins_field` because the reward is new game content absent from the published journal schema; if the live journal names it differently, only the taxonomy value changes. | Adding coins into a credit total; hardcoding the coin journal field name in the domain. |
| The net credit change read from the balance, not folded from the moments. | The credit delta on a moment prices income, because that is what the journal itemises. Spending mostly is not itemised in a form any rule could total, so a fold could never see a rebuy, an outfitting bill or a market purchase; a session that ended twenty million credits down reported a gain. Both ends of the balance are stated outright at every `LoadGame`, so their difference captures every outgoing whether or not the journal names it. | A net figure that silently means "earned"; chasing completeness by adding a spending rule per event type, which would be permanently one game update behind. |
| A purchase states its cost on a spend channel of its own. | The journal states a purchase cost in `TotalCost`, so reporting nought spent beside ten purchases was a figure the journal contradicted. Credits is the income channel, so routing a cost through it counts the money as banked and one large enough raised the major-payout milestone for buying a frame shift drive. Spending first borrowed the magnitude channel instead, which worked only while nothing summed magnitude across kinds: magnitude is also a jump distance in light years, so the two could never be totalled together. A third channel makes the distinction explicit and is what lets a session state what its priced events came to. | Giving a buy a `credits_field`, which folds spending into income; overloading magnitude, which cannot be summed across kinds; leaving a stated cost unread. |
| An unmeasured figure is omitted unless its slot is compulsory. | The credits card once read "Change unread" whenever the journal stated one balance. True and useless: it reports the absence of a single quantity out of the unbounded set the report did not measure, which is a rule that would fill the page if applied evenly. The value slot is the opposite case and keeps its wording, because something must occupy it or a blank card reads as a balance of nothing. So the test is whether the slot is compulsory, not whether the absence is interesting. | Announcing every quantity that went unmeasured; a blank mandatory slot a reader takes for zero. |
| A priced-events total, in a card of its own and never in the change slot. | "Change unread" is true whenever the journal states one balance and useless every time: it says nothing about a session that sold eighty modules. The journal prices a great deal of what a session did even when it never restates the balance; that total answers a real question. It is a fold over events where the balance change is a difference between levels, so the two are routinely different numbers; putting the fold in the credits card's delta slot would hand a reader one figure while they believed they were reading the other. It gets its own headline card, its own label and a note stating what it does not cover. | Presenting a priced total as the balance change; a delta slot whose meaning depends on which branch produced it; leaving a reader with "change unread" and nothing else. |
| An experimental effect is a moment of its own, told apart by a field's presence. | The journal reports applying an experimental effect as an `EngineerCraft` carrying the blueprint and grade already on the module, so it is indistinguishable from a grade roll by any value. Only the applying event carries `ApplyExperimentalEffect`; `ExperimentalEffect` is restated by every later roll on that module and so cannot separate them. Counting the two together made four effects and thirty rolls read as thirty-four modifications, which describes work that did not happen. | Matching on the restated field, which would count every subsequent roll as another experimental; one engineering figure that conflates two different kinds of work. |
| Outfitting and shipyard trade counted per side, with what cannot be counted declared. | Modules and ships bought and sold were absent from the report entirely, so a session that sold eighty stored modules for nearly two billion credits showed a balance change with nothing to account for it. Each side keeps its own count and its own sum, because a refit that spent on new modules and recovered money on the old is not the same session as one that did neither and a net figure reports them identically. Two things the journal will not support are stated in the section note rather than silently missing: a Vessel Hangar bay uses the same outfitting events and is counted under the vessel instead; a ship taken in part-exchange is priced inside the purchase event and stated as no sale at all. | A single net outfitting figure; counting a hangar bay twice; implying the totals are the whole trade when the journal does not state it. |
| The credit balance is dated, never derived. | A balance from `LoadGame` is hours old by the end of a long session, so the obvious repair is to apply every priced event to it. Measured against a real journal, which states the true answer at the next login, that derivation matched on two of fifty-four active spans and was out by a median of about eight million credits; four spans moved the balance with no priced event in them at all and the residuals ran both ways, so no missing rule would close it. The journal does not state every credit movement, so the reading is reported with the moment it was taken instead. | A derived closing balance presented as a balance; a figure confidently wrong by millions on exactly the sessions a reader would consult it for. |
| A carrier distance derived from positions rather than read. | A `CarrierJump` states the destination `StarPos` but no `JumpDist`, so the only evidence of distance is the gap between consecutive arrivals. That gap is measurable for every leg except the first of a session, whose origin the session never states. The rollup therefore carries the measured leg count beside the distance and the report names it, rather than presenting a short total as the whole. | Inventing an origin for the first jump; reporting an incomplete total as though it were complete; leaving the distance out because it cannot be read directly. |
| Session isolation by `Shutdown` bracketing. | A session is one game run, bounded by `Shutdown` events; the latest is the run ending at the last `Shutdown`. Anchoring on `Shutdown` rather than `LoadGame` keeps a run that returned to the main menu (which fires a fresh `LoadGame`) whole. Defining it structurally means a previous session can never bleed into the current debrief. | Heuristic session boundaries, time-window guesses and shrinking a run to its final leg by anchoring on `LoadGame`. |
| A history report paged into a bundle, not accumulated into one document. | A history report is regenerated every time the game closes and grows for ever, so one document eventually stops being openable and is rewritten whole on every quit. Splitting it into an index and a page per month, with one shared stylesheet rather than the palette repeated on every page, keeps each page small and lets an unchanged page be left alone. The session report is deliberately exempt: it is small and being able to hand somebody the whole file is the point of it. | A single history document that grows without limit; a bundle for the session report, which would cost its portability for nothing. |
| Pages keyed on the period they cover, filled from the oldest row. | A page named for its position renumbers the moment a page is added at the newest end, so the first session of a new month would rewrite every file in the bundle. A calendar month never changes once it is over, so a page keyed on it keeps its name for good and filling a month from its oldest row forward means only its newest part can move. That is what makes the incremental write worth having: the boundaries are deterministic, so identical bytes really are identical. | Position-numbered pages; paging by a fixed count from the newest entry, which shifts every boundary each time the newest page grows. |
| The month list on the index alone, with the pages anchored back to it. | Prev and next on their own make an old month a walk through every page in between, which is not navigation. A list of every month fixes that but it gains an entry each new month, so carrying it on every page would rewrite the whole bundle monthly and undo the paging. The index is rewritten on every run regardless, so the list lives there and each page links back to it by anchor, landing the reader on the list rather than at the top of a report whose log sits far below. Any month is then two clicks from anywhere. | A month list duplicated onto every page; navigation that only steps one page at a time; an index link that drops the reader above the whole report and leaves them scrolling. |
| The whole history's tab counts held in the stylesheet, not in each page. | A tab has to state the figure for the whole history rather than for the page or a reader cannot tell thirteen here from thirteen altogether. That figure changes on every session, so writing it into each page's markup would rewrite forty pages a quit and undo the paging. The stylesheet is one small file already rewritten on each run, so the counts are generated content in it and the pages carry only what is on them. It stays CSS, so the bundle still needs no JavaScript. | Per-page counts, which mislead; global counts in page markup, which defeat the incremental write; a script to fill them in, which the whole product rules out. |
| A rollup that bounds the report, offered but not imposed. | Paging divides a report; it does not bound it, so a journal gaining a thousand rows a month gains a page a month for ever. Folding the older tail into one row per day per category is the only option here that bounds the total and it does so by discarding detail, which is why it is off by default and the report says what it dropped. Its threshold is measured back from the newest row rather than from the wall clock, so an unchanged journal renders identically tomorrow and no page is rewritten by the passage of time alone. | An unbounded report; a rollup imposed on a reader who wanted the detail; a threshold anchored to "now", which would silently re-cut the same journal every day. |
| An event is filed by what the journal reports, not by what a player might have been doing. | `ApproachSettlement` fires when the ship flies within range of a settlement, whether or not anybody leaves the cockpit. Filing it under On Foot read the event as an intention rather than as the fact it states, so a session that approached three settlements from the pilot's seat reported three settlements on the On Foot card with no `Disembark` anywhere in it. It now counts under Travel as "Settlements approached", which is what the journal actually said. The rule generalises: a domain is chosen from the event's own evidence and its wording says only what the event states. | Inferring activity the journal never recorded; a card that reports a mode the commander never entered; wording ("Arrived at", "Visited") that claims more than proximity. |
| Reads bounded to the session, not the journal history. | A debrief is a function of one session's bytes, so reading the entire journal to produce one was waste that grew without limit as a Commander's logs piled up. The last-session read walks back only to the previous `Shutdown`, the all-history read streams file by file and the background recorder keeps only the current session. | Loading the whole journal history into memory for a debrief; an always-on watcher whose memory grows with uptime. |

## Quality enforcement

The structure is held in place by the structural tests listed against the invariants, by constructor injection through a single composition root and by a 100% line and branch coverage gate on `o7debrief.domain`, `o7debrief.application`, the whole of `o7debrief.infrastructure`, `installer.ops` and `installer.state`. Both UI layers are integration-tested and deliberately excluded from the hard coverage gate, because their correctness lives in a real Qt event loop rather than in branch coverage of pure logic. Infrastructure is gated as well as integration-tested: it still runs against sample journals and real temporary directories, with the decisions its adapters make (which candidate paths discovery builds, how a malformed line is treated, what a rotated file means) asserted directly. The 400-line module limit covers `o7debrief/`, `installer/`, `tests/` and the repository root, with the composition root and the delivery scripts exempted by name. The testing strategy is documented in [TESTING.md](TESTING.md) and the build-from-source workflow in [DEVELOPMENT-README.md](DEVELOPMENT-README.md).
